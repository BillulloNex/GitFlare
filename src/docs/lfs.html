Large files on GitFlare

Git history is stored in Cloudflare Artifacts, which caps a single blob at 32 MB and a repository at 1 GB. Anything bigger goes through Git LFS, stored in R2. Stock git lfs works with no extra configuration.

Set up once

git lfs install                      # once per machine
git lfs track "*.psd" "models/*.bin" # patterns for this repo
git add .gitattributes
git commit -m "Track large files with LFS"

From then on, git add, commit, push, clone and pull behave as usual. LFS discovers the server from the clone URL and reuses the same API key.

Push rejected with a recipe?

That means a blob over 32 MB was committed without LFS. The message lists the exact commands. If the file was added in the last commit:

git lfs install
git lfs track "*.bin"               # the large file's extension or path
git add .gitattributes
git commit --amend --no-edit
git push

If the file is in an earlier commit of the push, rewrite the pushed history instead:

git lfs migrate import --include="*.bin" --everything
git push --force-with-lease

presigned5 GiBR2 API credentials are configured; bytes go straight to R2.

Each repository can lower its own cap or disable uploads in its settings. Check the current policy with GET /api/repos/<repo>/lfs, gitflare lfs status <repo>, or the gitflare_lfs_status MCP tool.

CI

# .gitflare/ci.yml
checkout:
  lfs: auto     # auto (default) | true | false

auto runs git lfs pull when .gitattributes tracks LFS paths and git-lfs is in the job image, otherwise it warns and leaves pointer files. true fails the checkout when git-lfs is missing. A reference image with git-lfs is published as ghcr.io/<owner>/gitflare-ci:node22; point the runner at it with CI_IMAGE.

Not supported

  • File locking (git lfs lock) — GitFlare's model is a branch per task.
  • Objects over 5 GiB (multipart transfer).
  • Mirroring LFS objects to GitHub — pointer files mirror, the binaries stay in R2.
